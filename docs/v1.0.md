# BinX v1.0.0 — Complete Local Toolkit

BinX v1.0.0 is the first release intended as a stable, complete local binary-analysis toolkit. It finishes the v0.x feature line and freezes the architecture around reusable analysis libraries, deterministic renderers, and an intentionally offline execution model.

## Architecture

v1 separates the application into four layers:

1. Core library — binary storage, bounded byte reading, shared text helpers, hashing and public error/result types.
2. Format library — PE, ELF and Mach-O decoding plus format detection.
3. Analysis library — byte analysis, dependencies, disassembly, symbols/debug, diff/size, crash dumps and unified reports.
4. CLI layer — argument parsing, command classification, command runner, output routing and presentation.

The binx_core static library contains layers 1–3. The binx executable contains only the CLI composition layer.

## Safety model

Inputs are treated as hostile data. BinX does not execute inspected files, load target DLLs, invoke TLS callbacks, resolve libraries by loading them, access symbol servers, or make network requests.

Resource-sensitive operations are bounded by explicit parser checks and command-level result limits. Dependency resolution is filesystem-based and deterministic.

## Build and test

Windows:

    cmake -S . -B build
    cmake --build build --config Release
    ctest --test-dir build -C Release --output-on-failure

Linux:

    cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
    cmake --build build
    ctest --test-dir build --output-on-failure

Presets:

    cmake --preset release
    cmake --build --preset release
    ctest --preset release

Sanitizers on GCC/Clang:

    cmake --preset asan
    cmake --build --preset asan
    ctest --preset asan

Packages are generated with CPack:

    cpack --config build/CPackConfig.cmake

## Compatibility

The project requires a C++20 compiler and CMake 3.20 or newer. Windows uses CNG for hashing; non-Windows builds use OpenSSL Crypto.

## Post-v1 boundary

Cloud APIs, telemetry, hosted symbol services, online enrichment, GUI applications and remote analysis are deliberately outside the v1 boundary. They can be built on top of the stable local library/API rather than coupled into the core.

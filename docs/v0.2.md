# BinX v0.2 Engineering Plan - Deep PE Analysis

## Release goal

v0.2 turns the v0.1 metadata foundation into a serious Windows Portable Executable inspector.

The release remains fully local. There is no cloud API, authentication service, hosted storage, telemetry pipeline or web dashboard.

Central principle:

Parse the PE file into a validated internal model once, then let every command render that model.

Do not make imports, sections, exports and inspect each implement their own PE parsing.

## 1. Supported scope

v0.2 focuses on PE32 and PE32+.

Primary inputs include EXE, DLL, SYS and other PE-derived images.

Architectures:
- x86
- x86-64
- ARM
- ARM64

Unknown machine values remain representable as raw numeric values.

ELF, Mach-O, disassembly, symbols, dependency resolution and crash analysis are not expanded in v0.2. Their v0.1 detection behavior must keep working.

## 2. PE object model

Introduce a dedicated PE model rather than continuing to put PE-specific fields into generic metadata.

Conceptual model:

    BinaryFile
        |
        +-- BinaryMetadata
        |
        +-- PEImage
              |
              +-- DosHeader
              +-- CoffHeader
              +-- OptionalHeader
              +-- DataDirectories
              +-- Sections
              +-- Imports
              +-- Exports
              +-- Relocations
              +-- TLS
              +-- Resources
              +-- DebugDirectory

BinaryFile remains responsible for loading bytes and selecting a format.

The PE parser becomes responsible for turning those bytes into a PEImage.

## 3. PE parser phases

### Phase A - DOS header

Validate:
- enough bytes for the DOS header
- e_magic equals MZ
- e_lfanew is inside the file

Store at least e_magic and e_lfanew.

Do not assume the PE header immediately follows the DOS header.

### Phase B - NT signature

Validate:
- four bytes are available at e_lfanew
- signature is PE followed by two NUL bytes

Failure is a structured parse error, not a process crash.

### Phase C - COFF header

Parse:
- Machine
- NumberOfSections
- TimeDateStamp
- PointerToSymbolTable
- NumberOfSymbols
- SizeOfOptionalHeader
- Characteristics

Retain the raw values even when BinX does not use them yet.

### Phase D - Optional header

Validate the declared size before reading any field.

Recognize:
- PE32, magic 0x10B
- PE32+, magic 0x20B

Parse:
- AddressOfEntryPoint
- ImageBase
- SectionAlignment
- FileAlignment
- SizeOfImage
- SizeOfHeaders
- Subsystem
- DllCharacteristics
- NumberOfRvaAndSizes

Handle PE32 versus PE32+ layout explicitly. Do not rely on packed C++ structs.

### Phase E - Data directories

Read only the directory count actually present.

Expose:
- export table
- import table
- resource table
- exception table
- security directory
- base relocation table
- TLS table
- load config
- debug directory
- delay import
- CLR/runtime header

Each directory should contain:
- RVA
- declared size
- presence state
- validation state
- safe file mapping when one exists

Never parse a directory until its declared range is validated.

## 4. RVA mapping engine

This is the most important v0.2 utility.

Add reusable mapping:

    RVA -> section -> file offset

and, where possible:

    file offset -> RVA

Understand:
- section virtual address
- section virtual size
- section raw pointer
- section raw size
- image headers
- alignment

Rules:
- header RVAs can map into file headers
- section RVAs map only when inside valid section ranges
- virtual tail bytes without raw backing are not treated as file bytes
- integer overflow is checked
- impossible mappings return structured errors

Imports, exports, resources and relocations must use this mapper.

Do not duplicate RVA arithmetic in individual parsers.

## 5. Section parser

Add:

    binx sections app.exe

For every section expose:
- index
- name
- virtual address
- virtual size
- raw file offset
- raw size
- characteristics
- readable
- writable
- executable
- discardable
- shared

Human output should include a compact table.

JSON must retain raw numeric values separately from formatted display strings.

## 6. Section validation

Validate:
- section-table entry is inside the file
- raw pointer is representable
- raw size does not extend beyond EOF
- virtual address plus virtual size does not overflow
- section overlaps are detected
- suspicious alignment is diagnosed
- raw and virtual size relationships are recorded

Prefer diagnostics over blanket rejection. An unusual section is not automatically corrupt.

## 7. Import parser

Add:

    binx imports app.exe

For every imported DLL expose:
- DLL name
- import name
- ordinal import state
- hint where available
- thunk/IAT RVA
- file mapping when available

Handle:
- name imports
- ordinal imports
- 32-bit thunk widths
- 64-bit thunk widths
- malformed thunk chains
- imports whose data is outside valid mappings

Never treat an RVA as a host pointer.

## 8. Export parser

Add:

    binx exports app.dll

Expose:
- ordinal
- RVA
- function name
- forwarder string when present
- name ordinal base

Detect forwarders by checking whether an exported RVA lies within the export-directory range.

## 9. Relocations

Add:

    binx relocations app.exe

Parse base-relocation blocks.

Expose:
- block RVA
- block size
- relocation type
- target RVA
- target file offset when mapped

Support common x86, x64 and ARM64 relocation forms.

Unknown relocation types remain visible as raw numeric values.

## 10. PE characteristics

Decode important COFF and DLL-characteristic flags:

COFF:
- executable image
- DLL
- system file
- large-address aware
- 32-bit machine
- debug stripped
- relocations stripped

DLL characteristics:
- ASLR / dynamic base
- NX compatibility
- high-entropy VA
- CFG-related flags where represented
- terminal-server aware

Report flags descriptively. Do not turn a single flag into a claim that the whole binary is secure.

## 11. Resource directory

Add:

    binx resources app.exe

Enumerate:
- type
- name or numeric identifier
- language
- RVA
- size
- code page

Recognize common resource types where possible:
- ICON
- VERSION
- MANIFEST
- STRING
- DIALOG

The first v0.2 boundary is a correct, safe resource tree. Full decoding of every resource payload stays later.

## 12. TLS directory

Expose:
- TLS raw-data start/end
- zero-fill size
- TLS index address
- callback array address
- callback RVAs when safely mapped

Callbacks are metadata only. BinX never executes them.

## 13. Debug directory metadata

Detect and describe:
- debug directory RVA/size
- debug type
- raw location
- CodeView presence
- RSDS signature
- PDB path when safely decodable
- GUID
- age

PDB symbol loading stays in v0.7.

## 14. Improved inspect

Upgrade:

    binx inspect app.exe

to aggregate:
- file information
- PE header
- section summary
- import count
- export count
- resource presence
- relocation presence
- TLS presence
- debug information presence
- security-characteristic flags
- validation warnings

Keep info concise.

## 15. CLI commands added

Primary:
- sections
- imports
- exports
- resources
- relocations

Keep global options:
- --json
- --output
- --verbose
- --quiet
- --help

## 16. JSON model

JSON must be structured data, not serialized terminal text.

Conceptually:

    {
      "format": "PE32+",
      "headers": {},
      "sections": [],
      "imports": [],
      "exports": [],
      "resources": {},
      "relocations": [],
      "tls": {},
      "debug": {},
      "warnings": []
    }

Keep JSON schema versioned internally.

Addresses and other values that can exceed JavaScript exact integer precision should be strings.

## 17. Diagnostic model

Move beyond one generic parse-error string.

A diagnostic should conceptually contain:
- severity
- parser component
- file offset
- RVA when relevant
- stable diagnostic code
- human message

Example:

    WARNING PE_SECTION_RAW_RANGE
      section=.data
      file_offset=0x4200
      message=raw section range overlaps end of file

Fatal failures should stop only the affected analysis component.

A broken resource directory must not prevent section analysis.

## 18. Parser recovery

Prefer partial analysis.

Example:

    header_status = valid
    sections_status = valid
    imports_status = malformed
    exports_status = valid

This allows BinX to remain useful with damaged real-world binaries.

## 19. Testing strategy

Valid fixtures:
- minimal PE32
- minimal PE64
- normal EXE
- normal DLL
- ARM64 PE
- PE with imports
- PE with exports
- PE with resources
- PE with TLS
- PE with relocations
- PE with debug directory
- multi-section PE

Malformed fixtures:
- bad MZ
- bad PE signature
- e_lfanew outside file
- truncated COFF
- impossible optional-header size
- invalid section table
- section raw data past EOF
- overlapping sections
- import RVA outside image
- unterminated thunk array
- export table outside file
- invalid relocation block size
- malformed resource tree
- integer-overflow boundary cases

Fuzz parser entry points with arbitrary byte spans.

Never:
- crash
- hang
- read out of bounds
- allocate absurd memory from a malformed count

## 20. CLI integration tests

Add golden-output and structural JSON tests for representative binaries.

Test:
- exit codes
- headings
- JSON validity
- --output
- --quiet
- malformed-input behavior
- deterministic ordering where practical

## 21. Performance

Parse the PE once per process invocation.

Recommended flow:

    bytes
      |
    PE parser
      |
    validated PEImage
      |
    command analysis
      |
    output

Build reusable indexes for section ranges and data directories.

Do not sacrifice safety for pointer-based micro-optimizations.

## 23. Definition of done

v0.2 is complete when:
- PE32 and PE32+ parse reliably.
- Sections work on real Windows binaries.
- Imports and exports are enumerated.
- Relocations are parsed.
- Resources are safely enumerated.
- TLS metadata is exposed.
- Debug-directory metadata is exposed.
- PE flags are decoded descriptively.
- RVA/file-offset mapping is centralized and heavily tested.
- Malformed binaries produce diagnostics instead of crashes.
- All v0.1 commands continue working.
- JSON exposes structured PE data.
- Windows and Linux CI remain green.
- No input binary is executed or loaded.
- No cloud service is required.

## 24. Version boundary

Do not pull later roadmap features into v0.2:
- no full disassembler
- no PDB symbol engine
- no DWARF engine
- no binary diff
- no crash-dump engine
- no dependency resolver
- no hosted API
- no authentication
- no web dashboard

v0.2 is the deep PE inspection release.
